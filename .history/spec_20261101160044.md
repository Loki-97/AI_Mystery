# 1. PROJECT OVERVIEW

## 1.1 Project Description

AI Mystery Room is an AI-powered interactive detective investigation platform where users become investigators and solve fictional mystery cases generated dynamically using Artificial Intelligence.

Users provide a short scenario, story, or mystery premise. Based on the user's input, the backend AI generates a complete fictional investigation containing:

- A mystery storyline.
- A list of suspects.
- One actual culprit.
- Motives and character backgrounds.
- Investigation evidence.
- WhatsApp-style conversations.
- Images and photographs.
- CCTV recording representations.
- Witness statements.
- Timeline of events.
- Hidden clues and contradictions.

The user explores the generated evidence, analyzes the information, identifies inconsistencies, and ultimately selects the person they believe committed the crime.

The application evaluates the user's final decision against the actual culprit established during case generation.

## 1.2 Product Vision

Create an immersive detective experience in which every investigation feels like solving a real mystery.

The AI must generate believable fictional cases with logically connected evidence. Users should not simply guess the culprit; they should investigate, analyze, connect clues, and make evidence-based decisions.

## 1.3 Core Product Flow

1. User visits the website.
2. User enters a mystery scenario or story.
3. User configures the investigation difficulty.
4. User clicks Generate Mystery.
5. Backend sends the scenario to Gemini.
6. Gemini generates the investigation structure.
7. Backend validates and stores the generated case.
8. AI-generated evidence assets are created or retrieved through configured media providers.
9. User enters the Mystery Room.
10. User explores suspects and evidence.
11. User analyzes conversations, images, CCTV, and witness statements.
12. User selects the suspected culprit.
13. User submits the final accusation.
14. Backend evaluates the answer.
15. User receives the investigation result, explanation, and evidence-based reasoning.

# 7. MYSTERY CREATION MODULE

## 7.1 User Input

The user must provide a scenario or story.

Example:

"A wealthy businessman was found dead inside his locked office at midnight. Five people had access to the building. The security camera stopped working for 20 minutes. Everyone claims they were somewhere else. Find the murderer."

## 7.2 Input Fields

Required:

- Mystery Scenario.

Optional:

- Mystery Title.
- Difficulty Level.
- Number of Suspects.
- Investigation Type.

## 7.3 Difficulty Levels

**Easy**
- 3 suspects.
- 5–7 evidence items.
- Clearly identifiable clues.
- Limited misleading evidence.

**Medium**
- 4–5 suspects.
- 8–12 evidence items.
- Multiple contradictions.
- More complex motives.

**Hard**
- 5–7 suspects.
- 12–18 evidence items.
- Interconnected clues.
- Multiple red herrings.
- Complex timelines.
- Requires combining several pieces of evidence.

The selected difficulty should guide the AI generation process.

## 7.4 Generate Mystery

When the user clicks Generate Mystery:

1. Validate the input.
2. Send the request to the backend.
3. Create a mystery generation job.
4. Call Gemini.
5. Validate the AI-generated response.
6. Store the mystery and its evidence.
7. Initiate media generation jobs.
8. Return the generated mystery ID.
9. Redirect the user to the investigation room when the case is playable.

Show appropriate loading and generation progress states.

# 8. AI MYSTERY GENERATION ENGINE

This is the core intelligence of the application.

## 8.1 Gemini Responsibilities

Gemini must generate a complete investigation from the user's scenario.

The generated investigation must contain the following sections.

### A. Mystery Information

- Mystery ID.
- Mystery title.
- Scenario description.
- Crime location.
- Crime date and time.
- Crime type.
- Difficulty level.
- Case introduction.

### B. Suspects

Each suspect must contain:

- Suspect ID.
- Full Name.
- Age.
- Occupation.
- Profile description.
- Relationship with the victim.
- Possible motive.
- Alibi.
- Personality.
- Hidden information.
- Suspicion level.

The suspicion level is an internal investigation attribute. Do not automatically reveal it to the user.

### C. Culprit

Exactly one actual culprit must be selected.

The culprit must contain:

- Suspect ID.
- Motive.
- Opportunity.
- Method.
- Actual sequence of events.
- Explanation of how the crime was committed.

IMPORTANT:

The actual culprit must be established during initial mystery generation and must never change during an investigation.

Store the culprit separately from publicly accessible mystery data.

### D. Evidence

Generate multiple evidence items.

Each evidence item must contain:

- Evidence ID.
- Evidence title.
- Evidence category.
- Description.
- Content.
- Related suspect IDs.
- Discovery location.
- Discovery time.
- Clue classification.
- Relevance.
- Asset status.

Evidence categories:

1. WhatsApp Conversations.
2. Images and Photographs.
3. CCTV Recordings.
4. Witness Statements.
5. Documents.
6. Call Records.
7. Physical Evidence.
8. Timeline Records.

### E. Investigation Timeline

Generate a chronological timeline covering:

- Events before the incident.
- Events during the incident.
- Events after the incident.
- Suspect movements.
- Important interactions.
- Crime occurrence.

The timeline must be consistent with all evidence.

### F. Hidden Clues

Generate clues that help users identify the actual culprit.

Examples:

- A suspect provides an incorrect alibi.
- A WhatsApp conversation contradicts a witness statement.
- CCTV footage reveals an unexpected movement.
- A timestamp does not match the suspect's explanation.
- A photograph reveals an important object.

### G. Red Herrings

Generate believable misleading evidence.

Red herrings must create reasonable suspicion without making the actual solution logically impossible.

The final investigation explanation must clarify why misleading evidence was not sufficient to establish guilt.

## 14.1 Mystery Generation Instructions

Gemini must follow these rules:

1. Generate a fictional mystery based on the user-provided scenario.
2. Generate exactly one culprit.
3. Ensure every suspect has a believable background.
4. Create realistic motives and alibis.
5. Ensure evidence is interconnected.
6. Create meaningful clues.
7. Include reasonable red herrings.
8. Maintain chronological consistency.
9. Ensure the actual culprit can be identified using available evidence.
10. Never change the culprit after case generation.
11. Return valid structured JSON.
12. Follow the requested difficulty level.
13. Avoid graphic or excessively disturbing descriptions.
14. Use entirely fictional people, organizations, locations, and records.

## 14.2 Evidence Consistency

The AI must ensure:

- Evidence timestamps are consistent.
- Conversations match the investigation timeline.
- Suspect statements match their generated backgrounds.
- Contradictions are intentional.
- At least two independent clues support the final culprit identification.
- No essential clue exists only in hidden solution data.

## 14.3 Structured AI Response

Use a predefined JSON schema for all generated investigations.

Validate the response using a schema validation library such as Zod.

If generation fails:

- Retry with a controlled retry limit.
- Log the failure.
- Never save incomplete investigations as playable.
- Return a meaningful error message.

# 16. BACKEND API SPECIFICATION

Use REST APIs with a consistent JSON response format.

Base URL:

/api/v1

## 16.1 Authentication APIs

POST /auth/register

POST /auth/login

POST /auth/logout

GET /auth/me

## 16.2 Mystery APIs

POST /mysteries

Generate a new mystery from the user's scenario.

GET /mysteries

Retrieve the authenticated user's mysteries.

GET /mysteries/:id

Retrieve a mystery's public investigation details.

GET /mysteries/:id/status

Retrieve generation and media processing status.

DELETE /mysteries/:id

Delete an owned mystery and its associated records.

## 16.3 Suspect APIs

GET /mysteries/:id/suspects

GET /mysteries/:id/suspects/:suspectId

## 16.4 Evidence APIs

GET /mysteries/:id/evidence

GET /mysteries/:id/evidence/:evidenceId

## 16.5 Investigation Notes APIs

GET /mysteries/:id/notes

POST /mysteries/:id/notes

PUT /mysteries/:id/notes/:noteId

DELETE /mysteries/:id/notes/:noteId

## 16.6 Accusation APIs

POST /mysteries/:id/accusations

GET /mysteries/:id/result

The result endpoint must reveal the solution only after a valid final accusation has been submitted.

## 16.7 API Response Format

Success:

{
  "success": true,
  "message": "Mystery generated successfully",
  "data": {}
}

Failure:

{
  "success": false,
  "message": "Unable to generate mystery",
  "error": {
    "code": "MYSTERY_GENERATION_FAILED"
  }
}

Use appropriate HTTP status codes.

# 22. MYSTERY GENERATION WORKFLOW

The following workflow defines the expected backend process.

1. Receive user scenario.
2. Validate scenario and configuration.
3. Create mystery generation record.
4. Send structured generation prompt to Gemini.
5. Receive investigation JSON.
6. Validate JSON against the mystery schema.
7. Validate suspect count and culprit references.
8. Validate evidence relationships and timeline consistency.
9. Run investigation solvability checks.
10. Save mystery data.
11. Save suspects.
12. Save confidential solution separately.
13. Save evidence.
14. Initiate media generation jobs.
15. Update generation status.
16. Make the mystery playable when its minimum required data is ready.

The case must be playable even if optional media generation fails.

# 27. IMPORTANT BUSINESS RULES

These rules are mandatory and must not be violated.

1. Every mystery must have exactly one actual culprit.
2. The culprit must be established before the investigation begins.
3. The culprit cannot change during the investigation.
4. Every suspect must belong to one mystery.
5. Every evidence item must belong to one mystery.
6. Evidence must be logically consistent with the generated investigation.
7. The user must have sufficient evidence to identify the culprit.
8. Red herrings must not make the correct answer impossible to determine.
9. The actual solution must never be exposed before final accusation.
10. Only the backend can evaluate the accusation.
11. Users can access only their own mysteries.
12. A completed mystery cannot accept another final accusation.
13. Media generation failures must not destroy the investigation.
14. AI output must be validated before database persistence.
15. The application must clearly distinguish fictional evidence from genuine records.

# 29. FINAL PROJECT DEFINITION

AI Mystery Room is a full-stack AI-powered mystery investigation platform built using the MERN stack and Google Gemini.

Its primary purpose is to transform user-provided scenarios into complete fictional detective investigations with suspects, motives, interconnected clues, AI-generated evidence, and a predetermined culprit.

Users investigate the case by exploring evidence, analyzing contradictions, and selecting the person they believe committed the crime.

The backend evaluates their accusation and reveals the complete investigation solution.
